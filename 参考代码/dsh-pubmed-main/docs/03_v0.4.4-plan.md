## 0. 为什么是这个版本（背景与判断）

v0.4.2/v0.4.3 把"检索 → OA 发现 → 全文 → 图谱"串联链路彻底打通后，dsh-pubmed 的**功能面已经收敛**——26 个工具覆盖了从发现到沉淀的完整工作流。继续往上堆工具，边际收益递减，还会稀释"免费直连 + 纯 JS 免构建"的清晰定位。

真正还欠的不是"更多能力"，而是**四条一致性与健壮性的尾巴**：

1. **端点可配不一致**——P3.8b（v0.4.0）给 EUTILS/EPMC/PUBTATOR 三族做了 `*_BASE_URL` 可配，但 v0.4.x 新增的 OpenAlex、S2 两个数据源反而**硬编码**，破坏了自建的统一模式。
2. **图谱是用户的"长期知识资产"，但版本号是个摆设**——`newGraph()` 带 `version:1`，`loadUserGraph` 却从不读它，未来结构演进没有迁移入口。
3. **S2 是"补充源"，却能拖垮整个多源搜索**——无 key 共享池限流时，6 次指数退避让单次 S2 调用拖到 60–90s。
4. **内存卫生与参数回退**——`sessionGraphs` 永不淘汰、`sessionKeyOf` 只有一层回退，均为 02 分册缓议项。

这四项互相独立、风险各自隔离，适合合成一个聚焦的 v0.4.4；**总工作量约 1.5 天**（2026-09-30 修订：P2 由"只挂空钩子"改为"显式步骤表 + 结构规整"后的重新估算，见 §10 R9）。下面逐项给详细设计。

## 2. P2 · 用户图谱 schema 迁移钩子

### 2.1 现状盘点

- `newGraph()`（core:2687）已带 `version: 1`。
- `loadUserGraph`（core:3072 → `deps.storage.loadUserGraph`，实现在 index.js:192）只校验 `data.nodes && data.edges` 存在，**不读 `version`**。
- `mergeGraphs`（core:2999）幂等合并已正确（node 按 id 去重、sources 并集、weight 累加、lastSeen 刷新）——**跨会话合并无隐患，本项不动它**。

### 2.2 问题

`version` 字段目前是"写了不用"的死字段。一旦 v0.5 需要调整节点/边结构（例如 concept 节点增加新属性、边增加新 kind），老用户的 `~/.dsh/dsh-pubmed-graph.json` 会在 `graph_commit` 时**与旧结构静默混用**，且无报错、无迁移路径。这是"长期知识资产"叙事下唯一的结构性短板。

> **架构约束（必须先讲清）**：core 以 `new Function` 求值、无模块加载能力（见 02 分册一.6），**迁移逻辑必须内联在 core 内**，不能抽成独立 `migrations.js`。本项只做"**显式步骤表 + 结构规整**"这一步到位的钩子，不引入通用迁移框架（2026-09-30 修订：原"纯挂空钩子"的方案被否，理由见 §10 R2/R3）。

### 2.3 详细设计

**core**——一个显式步骤表 + 一个结构规整函数，接入在 core 自己的 `loadUserGraph()` 包装上：

```js
// 图谱 schema 当前版本。newGraph 写入；读取用户图谱时经 migrateUserGraph 升级。
const GRAPH_SCHEMA_VERSION = 1

// 逐级迁移步骤表：MIGRATIONS[n] 把 v(n-1) 的数据就地升级为 v(n)。
// 未来新增结构时只在这里追加一步并 bump GRAPH_SCHEMA_VERSION，链条天然可扩展。
const MIGRATIONS = {
  // 2: (data) => { /* …v1→v2 结构调整… */ return data },
}

// mergeGraphs 假设 node.sources 是数组、node.count 是数字（core:3006-3007），
// 旧文件字段漂移会让合并抛错或产出 NaN —— 读取时统一补齐（修订 R3）。
function normalizeGraph(data) {
  if (!data || typeof data !== 'object') return null
  if (!data.nodes || typeof data.nodes !== 'object') return null
  if (!data.edges || typeof data.edges !== 'object') return null
  for (const n of Object.values(data.nodes)) {
    if (!Array.isArray(n.sources)) n.sources = n.sources ? [n.sources] : []
    if (typeof n.count !== 'number' || !isFinite(n.count)) n.count = 0
  }
  for (const e of Object.values(data.edges)) {
    if (typeof e.weight !== 'number' || !isFinite(e.weight)) e.weight = 0
  }
  return data
}

function migrateUserGraph(data) {
  const g = normalizeGraph(data)
  if (g === null) return null
  let v = parseInt(g.version, 10)
  if (!isFinite(v) || v < 1) v = 1              // 无 version 字段的远古文件视为 v1
  if (v > GRAPH_SCHEMA_VERSION) return g         // 未来版本：不降级、不臆测，原样返回
  for (let step = v + 1; step <= GRAPH_SCHEMA_VERSION; step++) {
    const fn = MIGRATIONS[step]
    if (typeof fn !== 'function') return g       // 缺迁移步骤：保留原版本，绝不"只盖版本戳"（修订 R2）
    g = fn(g) || g
  }
  g.version = GRAPH_SCHEMA_VERSION
  return g
}
```

- `newGraph()` 的 `version: 1` 改为 `version: GRAPH_SCHEMA_VERSION`；**并同步 core:3212**——`pubmed_graph_get` 空图回退里还硬编码着一个 `stats.version: 1`（修订 R7），两处都换掉才算真正的"单一来源"。
- **接入点（本轮最重要修订 R1）**：core 里 `loadUserGraph()` 有**两个**调用点——`pubmed_graph_get`（core:3211，scope=user）与 `pubmed_graph_commit`（core:3268）。只包 3268 会让 `graph_get(scope=user)` 读到未迁移结构。因此迁移**放进 core 自己的 `loadUserGraph()` 包装**（core:3072-3074），成为唯一咽喉点：

```js
function loadUserGraph() {
  const raw = (storage && storage.loadUserGraph) ? storage.loadUserGraph() : null
  return migrateUserGraph(raw)   // null 由调用方按既有 `|| newGraph()` / 空图分支处理
}
```

- **index.js 的 storage 层保持"哑"**：只负责读写文件，迁移归 core。理由：core 是唯一知道 schema 语义的地方，与 `newGraph`/`mergeGraphs` 同处一处，未来迁移步骤单一维护点；`storage.loadUserGraph() -> rawObject` 契约不变。

## 3. P3 · S2 429 退避上限

### 3.1 现状盘点（v0.4.2 实测新增缓议项）

- S2 走 `s2Get`（core:1977）→ `s2Scheduled`（gap：无 key 3s / 有 key 1.1s）→ `withNetRetry`。
- `withNetRetry` 对 `HTTP 429` 重试 `NET_RETRY_MAX = 6` 次，退避 1s→2s→4s→8s→16s→30s（cap 30s）。
- 无 key 共享池（100 req/5min/IP）重度限流时，**单次 S2 调用可拖 60–90s**；`pubmed_search_papers` 超时已因此被抬到 180s。
- 五轮真机回归记录：限流窗口内 `get_s2_detail` 连续超时，而同族（非 S2）工具重试成功。

### 3.2 问题

S2 定位是"**补充源**"（补被引数/推荐/全领域）。但在多源搜索里，它一旦进入限流窗口，6 次长退避会**拖慢整个四源合并结果**——用户为 PubMed/EPMC/OpenAlex 三源的结果，白白等 S2 的 90s。为"补充"付出"主干延迟"的代价，不划算。

### 3.3 详细设计

**原则**：S2 限流时**快速失败、优雅降级**，而不是长退避死等。给 `withNetRetry` 增加可选的重试预算参数，S2 调用点传入较小值；其余（NCBI/PubTator/EPM/OpenAlex）维持 6 次不变。

```js
// withNetRetry 签名扩展（向后兼容：不传 maxRetries 时仍用全局 6 次）
async function withNetRetry(fn, maxRetries) {
  const cap = (typeof maxRetries === 'number') ? maxRetries : NET_RETRY_MAX
  for (let attempt = 0; ; attempt++) {
    try { return await fn() } catch (e) {
      const blob = /* …现有… */
      if (attempt >= cap || !NET_RETRY_RE.test(blob)) throw new Error(humanNetError(e))
      /* …退避… */
    }
  }
}
```

```js
// S2 专用：限流窗口内快速降级。无 key 共享池下 429 频发，长退避会拖垮多源合并。
const S2_RETRY_MAX = 2   // 429 最多重试 2 次（1s+2s ≈ 3s 内见分晓），然后让该源报错、其余源照常
async function s2Get(pathAndQuery, signal) {
  const url = S2_BASE + pathAndQuery
  return await s2Scheduled(() => withNetRetry(() => httpGet(url, signal, PT_TIMEOUT_PROBE), S2_RETRY_MAX))
}
```

- **配套**：`pubmed_search_papers` 的 S2 分支本就 try/catch 隔离（per-source error 不影响他源），S2 快速抛错后 `perSource` 报告 `s2 error`，其余三源正常返回——**合并结果立等可取**。这正是我们要的行为，无需额外改动。
- **可选**：`S2_RETRY_MAX` 暴露为 config `S2_MAX_RETRIES`（默认 2），有 key 用户可调大。→ 决策：先内联常量，配置化留待真实需求（避免配置项膨胀）。
- **收益边界（修订 R10）**：多源循环是**串行** `for await`（core:1906-1916），S2 在 `sources: ['all']` 中排最后；默认 `sources` 甚至不含 s2（core:1868）。所以 P3 的收益精确表述是"**显式纳入 s2 时不再白等**"，而非"S2 会拖慢其他源的抓取"。
- **连带收尾（修订 R8）**：`pubmed_search_papers` 的超时（现 core:827，`180000`）其注释写着 "S2 429 backoff can exceed 60s alone" —— P3 落地后该 rationale 失效。**复查结论（2026-09-30）：超时维持 180s，仅更新注释**。数学：S2 429 路径现封顶 ~3s，但 S2 挂起路径仍为 3×30s 超时 ≈ 90s；叠加"另一源黑洞化（7 次快败 + 61s 退避 ≈ 63s）+ 其余健康源" ≈ 160s——这正是本插件要扛的区域黑洞场景，且超时中止会**丢弃已完成的健康源结果**。下调到示例的 90–120s 会截断该场景；180s 恰好覆盖。注释已改为新依据（见验收）。

## 4. P4 · sessionGraphs 内存上限 + sessionKeyOf 硬化

> 02 分册缓议项四.4 与二.2 的合并清仓。两项都小，合一个 P 编号。

### 4.1 现状盘点

- `sessionGraphs = new Map()`（core:3054）**永不淘汰**：每个 sessionKey 一个图，长会话/多会话累积，仅 DSH 重启清空。真实但边缘（会话隔离 + 重启即清）。
- `sessionKeyOf`（core:3064）只有一层回退：`(exec?.agent?.id) ?? 'default'`。真机已证 `agent.id` 存在（session-uuid），隔离实际生效——属"硬化"非"修 bug"。

### 4.2 详细设计

**(a) sessionGraphs 容量上限（LRU 式淘汰）**

> 现有 `getSessionGraph`（core:3067-3070）**已存在**——本项是**改造**它，不是新增（修订 R6）。

```js
const SESSION_GRAPH_MAX = 32   // 单进程最多保留的活会话图数；超出淘汰最久未用的
function getSessionGraph(key) {
  let g = sessionGraphs.get(key)
  if (g) {
    // LRU 触碰：delete+set 把该 key 移到 Map 尾部（Map 保持插入序）
    sessionGraphs.delete(key); sessionGraphs.set(key, g)
    return g
  }
  g = newGraph()
  sessionGraphs.set(key, g)
  // while 而非 if：即便一次进入多个 key、或 MAX 被调小，也能收敛到上限（修订 R6）
  while (sessionGraphs.size > SESSION_GRAPH_MAX) {
    const oldest = sessionGraphs.keys().next().value   // Map 首部 = 最久未用
    if (oldest === key) break                          // 绝不淘汰刚插入的当前会话
    sessionGraphs.delete(oldest)
    graphWriteChains.delete(oldest)                    // 写链同步清，避免第二个泄漏点
  }
  return g
}
```

- **风险点**：淘汰一个会话图后，该会话的 `graph_get` 会得到空图（不是报错）。现 `graphSummary` 已返回 `nodeCount`，空图自然 `nodeCount:0`，agent 可判。可接受，文档注明即可（§6 D4）。
- `graphWriteChains`（core:3057）同样按 key 累积——淘汰会话图时**一并删除对应写链**，否则写链 Map 成为第二个泄漏点（已并入上面的 `while` 体）。

**(b) sessionKeyOf 回退链硬化**

```js
function sessionKeyOf(exec) {
  const e = exec || {}
  const id = (e.agent && e.agent.id) || e.sessionId || e.requestId
  return id ? String(id) : 'default'
}
```

- 回退顺序 `agent?.id ?? sessionId ?? requestId ?? 'default'`：前三个字段任一存在即用它做隔离键，全部缺失才退化到共享 `'default'`（与现状一致，向后兼容）。

## 9. 风险与约束

- **`new Function` 架构约束**（02 分册一.6 重申）：core 无模块加载能力，**所有改动（含 P2 迁移逻辑）必须内联在 core 内**，不得抽独立文件 import。本计划全程遵守。

- **向后兼容**：P1 默认值与现状一致、P2 旧文件直通、P3 仅缩短 S2 退避（其余源不变）、P4 单会话路径不变——四项均为**纯增量/纯收紧**，无破坏性变更。
- **离线测试优先**：所有新断言走 mock，不进 smoke；真机仅抽查"配反代后 OpenAlex 源生效"一条。
