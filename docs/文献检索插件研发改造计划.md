# 文献检索插件研发改造计划

建议下一版集中交付一条完整路径：用户输入审稿人点名的 DOI，找到对应论文，先存题录；几天后取得 PDF，重开任务，把文件补到同一个 Zotero 条目。这个场景只涉及一篇论文，却能检验标识、持久化、文件管理和外部写入四个关键环节。同版提前显示逐源取回数量和已知的取数边界。随后再扩大单次检索规模，最后支持跨月更新。

本文依据 0.5.8 工作区（Git 基线 `99b2643`）及[《科研使用场景与插件优化建议》](./科研使用场景与插件优化建议.md)。下文的类型、文件布局和发布切分均为设计建议。外部接口能力需在对应阶段验证。

## 一、从代码理解科研流程

| 研究者的动作 | 软件里对应的对象 | 设计时要保住什么 |
| --- | --- | --- |
| 从两个库搜到同一篇论文 | 两条来源记录，一条供人阅读的题录 | 能追溯各自的来源、检索式和标识。去重后仍能复核或拆分。 |
| 先看摘要，再看全文决定是否采用 | 一篇报告可以经历多次筛读决定 | 决定要能关联到阶段、理由及当时看到的材料。暂时拿不到正文，只影响获取进度。 |
| 把论文加入 Zotero，后来补交附录 | 一个目标库条目、分类关系、若干附件 | 三者可能各自成功或失败，再次执行应从未完成的一步继续。 |
| 返修时检查新增论文 | 同一课题下两次检索，各有固定清单 | 上一轮里有哪些论文、用过哪个版本，即使本轮来源失败也应能还原。 |

工程上可以沿用现有分层。`src/search/` 负责将各源响应规范化并判断论文身份，`src/host/tasks/` 负责任务、轮次与写盘，`src/host/pdf/` 和 `zotero/` 执行外部操作。面板的 HTTP 路由与模型工具应调用同一项 Host 业务操作，使“补录一篇”和“只补附件”在两个入口得到相同结果。面板负责文件选择和人工确认，模型工具可查询待办与结果。无需先重排源码目录。

## 二、开发顺序与发布门槛

| 顺序 | 可独立验收的交付 | 为什么排在这里 |
| --- | --- | --- |
| 1 · 下一版 | 单篇精确补录、完整摘要、手工补 PDF、Zotero 分步结果；逐源取数提示 | 先解决已有任务重开后丢信息、重复操作可能重复建条目的问题。 |
| 2 · 检索基础 | 逐源执行记录、保留来源命中、可复核去重，再增加续检 | 翻更多页会放大误合并和重复计数。先能解释第一页，再处理第二页。 |
| 3 · 建集与筛读 | RIS 导入、引文扩检、分阶段筛读、准确导出 | 这些入口共享第二阶段的身份匹配、批次溯源和统计。 |
| 4 · 课题更新 | 关联已有任务、冻结投稿清单、附件归档、增量比较 | 到这一步，逐篇身份、决定、文件和目标条目都有可保存的依据。 |

### 1. 下一版按三个改动包实施

**1A　先修任务写盘，同时验证 Zotero 能力。** `TaskStore.save` 目前对摘要截取前 800 字符；列表已有独立的折叠逻辑。取消写盘截断，详情返回已取得的完整摘要，列表继续显示预览。区分上游未提供摘要与旧任务疑似已截断；仅凭末尾省略号无法断定时显示“完整性未知”。在临时数据目录保存一条关键句位于第 801 字符之后的记录，用新建的 Store 重新加载验证，避免内存缓存掩盖问题。[任务存储](../src/host/tasks/store.ts) · [界面预览测试](../test/abstract-preview.test.ts)

同时用本机 Zotero 测试库做一个小实验：保存题录，结束当前会话，重新定位目标父条目，再尝试加入分类、补附件并读回结果。分别记录接口能返回的库标识、持久条目键和可验证的附件信息。当前连接器的会话标识仅用于当次操作；跨会话能力决定 1C 可以自动补到哪一步。[连接器](../src/host/zotero/connector.ts)

**1A 实测（2026-11-25，Zotero 10.0.9）。** 在本机个人库的两个测试分类中，先通过 Connector 保存一条题录，再通过 Local API 读取 `Zotero-Server-ID`、库路径 `users/0` 和持久条目键。缺少原 Connector 会话时，`updateSession` 和 `saveAttachment` 均返回 `SESSION_NOT_FOUND`。取得本地写入授权后，通过 Local API 将同一个父条目加入第二个分类，并创建、上传和登记 PDF 子附件。读回确认两个分类各指向同一父条目，附件列表只有一项，文件与上传内容逐字节一致。实验使用独立 API 请求，覆盖原 Connector 会话不可用时的操作，尚未实测重启 Zotero、群组库或旧版 Zotero。1C 可用实例 ID、库路径和条目键定位目标，用附件键和文件校验值核验补传结果。本地写入需要启用 Local API 并取得授权。[Zotero Local API](https://www.zotero.org/support/dev/web_api/v3/local_api) · [文件上传](https://www.zotero.org/support/dev/web_api/v3/file_upload)

**1B　增加精确补录和 PDF 关联。** 在支持的数据源实现按 DOI、PMID、arXiv ID 查询的可选能力。Host 识别并规范化输入，逐项核对返回标识；保留 arXiv 显式版本。查无匹配、来源暂不可用、版本不符要返回可区分的结果。匹配成功后复用已有题录或在当前任务追加一篇，并记录“按标识补录”的来源。再次打开或重跑任务时仍能找到人工补录项；建议把手工加入的集合独立于当轮结果，展示时合并，统计时分别计数。

从论文详情选择本地 PDF，复用现有文件校验、SHA-256 和用户目录写入逻辑。记录摘要指纹、获得途径、时间和文件位置，首版材料角色只需支持正文。相同文件再次关联应复用已有记录；用户选错文件可解除关联，保留原文件。标识与文件无法可靠匹配时，由用户确认归属。[PDF 存储](../src/host/pdf/store.ts)

**1C　让转存可以接着做。** 目前连接器依次保存条目、移入分类、上传附件。分类失败时条目可能已创建，附件失败时服务仍可能写入 `synced`。将每篇的结果拆成“父条目、目标分类、各附件”三部分，持久化目标库、分类标识、可核验的父条目键、文件指纹和最近一次结果。每步成功即记录。遇到请求超时或写回失败，标为“待核对”，按 1A 验证过的能力先查目标；无法确认时显示人工步骤和文件位置。已有条目仅补缺项，相同目标与文件的并发请求合并处理。[同步写回](../src/host/tasks/service.ts) · [同步面板](../src/client/ZoteroSyncDialog.tsx)

**同步交付取数提示。** 每个“检索块 × 来源”显示本次请求上限、实际取回条数、是否已知还有下一页。现有 Provider 只返回规范化记录数组，若只能数出规范化后的条数，就明确标注该口径；上游总数、续页能力未知时保留“未知”。完整执行日志在阶段 2 交付。[Provider 契约](../src/search/types.ts)

**发布验收。** 以一个已知标识保存题录，再模拟分类失败、附件上传失败、成功后本地写回中断。重开任务应能指出各项已知结果和下一步。对支持跨会话补传的环境，连续补传两次，核对 Zotero 中只有一个父条目和一份对应 PDF；能力不足的环境应能定位待人工处理的条目或候选项，且重试不会再次建条目。

### 2. 先记录一次检索的事实，再做去重与续检

1. **在发送请求的位置生成执行记录。** 每条以任务、轮次、检索块、来源和页次定位。保存原检索式、适配后实际发送的表达式、年份及开放获取过滤条件、执行时间、停止原因。在 Provider 最后构造请求处采集允许记录的字段，避免只记到适配层、漏掉来源附加条件或把密钥写入导出件。一个块中的布尔条件由该源解释；多个块按并集合并。面板应能指出有损改写，例如字段或排除条件被移除。[检索适配](../src/search/query-adapter.ts) · [任务执行器](../src/host/tasks/runner.ts)
2. **明确统计的单位。** 逐页记录上游报告总数（可空）、实际返回数、成功规范化数、本地过滤后数。轮次级单列合并后数、合并后过滤与任务上限生效后的保存数。分页重复返回同一页不能累加；同源不同检索块的总命中也不能直接相加作独立论文数。保留现有 `rawHits` 语义供旧调用方使用。验收样例中让某源返回 40 条、过滤后剩 12 条，并放入跨源重复记录，要求从导出的明细能复算汇总。
3. **把来源记录与合并题录分开保存。** 复用已有 `PaperRecord` 和 `RankedHit`，保存规范化来源记录及其命中位置；`Paper` 用作阅读和排序结果。对 DOI、PMID 等建立多标识索引，在整组强标识一致时合并。共享 PMID 且一方缺 DOI 可合并；同题不同 DOI、冲突标识、疑似预印本与正式版进入复核。保存成员和匹配依据，拆分后能恢复原始成员。沿用已有 `paperId` 作为状态引用，为后补标识或合并建立别名；冲突的筛读结论并列待确认。用含“同时带 DOI 和 PMID”的桥接记录测试整组冲突，避免两次局部匹配串错三篇论文。[现有匹配与排序](../src/search/identity.ts)
4. **按来源逐步接入续页。** 给 Provider 增加可选分页结果，包含记录、可选总数、下一页游标或偏移量。老实现经适配器保留首页行为。选一个可用固定样例验证的来源先接通；按现行条款、限流及可用接口验证其余来源后逐个开放。每个“轮次 × 检索块 × 来源”独立保存条件指纹、页进度和停止原因。页记录和下一游标同次提交，成功后推进；取消或限流保留已提交页。条件变更开新轮，过期游标提示从新轮重检。面板区分浏览已存结果与向来源继续取回。

**发布验收。** 在固定多页响应中制造跨页重复、第二页中断、限流及成功零命中。恢复后论文集合、排序和计数应与连续执行一致；达到上限、已取尽、无法续页分别显示。再用熟悉课题的几篇已知论文检查漏在哪一步，将漏检原因记入样例。

### 3. 用同一套来源记录承接导入、扩检和筛读

| 交付顺序 | 具体实现 | 验收场景 |
| --- | --- | --- |
| RIS 导入与题录导出 | 给批次增加来源类别，外部库名独立于在线 Provider 枚举。保存文件指纹、检索日期、策略和解析失败位置。解析后送入阶段 2 的匹配流程。统一文献类型映射，供 RIS、BibTeX 和 Zotero 使用，保留原始类型与缺项。 | 导入含期刊、会议、预印本、重复项及坏记录的样例。重复导入不重复建篇，能定位坏记录；核对实际导入或编译后的作者、出处、类型与标识。 |
| 从种子论文扩检 | 向后追参考文献，向前找引用它的论文。一次操作建一个批次，记录种子、方向、来源和日期，复用分页与限流。 | 同一篇论文经搜索和引文两路进入，仅筛读一次，仍能查到两条发现路径；区分来源不支持与成功返回空集。 |
| 分阶段筛读 | 扩展现有逐篇标记，按题摘初筛、全文资格评估保存决定、理由、操作者及时间，改判保留前次决定。全文获取进度单独展示。CSV 同时支持当前结果及决定明细。 | 一篇缺全文的报告进入待获取清单；补到全文并排除后，可以从汇总数定位该篇、排除理由和所读材料。旧任务的单一标记保留为历史结论，阶段未知。 |

### 4. 用不可变清单支持投稿与返修

先做手动“保存投稿清单”。课题可关联多个现有任务，每次冻结时复制当时的逐篇标识、题录要点、检索批次、筛读决定、所读版本、附件指纹和 Zotero 去向。普通检索轮次只需保存可比较的成员和执行记录；投稿节点额外固定用户选用的材料。一篇报告可挂正文、附录、勘误，多个报告可显式关联为同一研究。涉及版本关系时记录依据，不确定则保留待核对。

随后扩展现有任务对比：以固定清单为基准，分列新发现、共有、本轮未见、已知新版本和待补全文，同时列出策略变化与失败来源。一次来源失败足以让旧论文从新结果中消失，因此“本轮未见”需要保留原记录。先完成可重复的手动更新，再考虑定时提醒。双人独立评审、仲裁及统计合并留待明确的团队需求。[轮次记录](../src/host/tasks/rounds.ts) · [现有对比逻辑](../src/host/tasks/compare.ts)

## 三、存储演进：在需要独立恢复时拆文件

目前任务正文在插件私有目录的 `tasks/<id>.json`，列表索引可重建。PDF 指纹缓存在私有目录，用户可读文件由 `pdfRoot` 或工作目录决定。建议保留这两类文件的生命周期，按以下时机增加结构。[数据目录解析](../src/host/paths.ts) · [任务持久化](../src/host/tasks/store.ts)

| 时机 | 建议布局 | 拆分的必要性 |
| --- | --- | --- |
| 阶段 1 | 继续在任务 JSON 中保存新增字段，给任务正文独立的格式版本；保留 `tasks/index.json` 作为派生索引。 | 单篇补录无须引入数据库。正文格式版本用于区分旧摘要、旧同步状态与新产生的结果，避免将旧 `synced` 推断为附件成功。 |
| 阶段 2 | 在私有目录增加 `runs/<taskId>/<roundId>/`。每页一份不可变文件，含来源记录、页统计和续页信息；轮次清单记录已提交页及顺序。 | 完整摘要、多页来源记录体积随检索增长。将它们独立保存，可重建合并结果，也避免每更新一次筛读状态就重写历史页。 |
| 阶段 4 | 课题导出目录包含 `manifest.json`、`baselines/<id>.json`、`materials/<指纹>.<扩展名>`。清单记录相对路径、文件角色、校验值及缺失项。 | 私有缓存可清理，用户也可能移动课题。独立导出一份可校验的材料和投稿清单，才能在另一目录中复原。 |

**写入与恢复顺序。** 阶段 1 先调整 Store 的错误传递。现有写队列会记录异常并继续，调用方需要能区分“本次保存失败”和“队列还能接受后续写入”。对损坏或更高版本的任务保留原件并报告原因。阶段 2 先写页临时文件并原子替换，再原子更新轮次清单，以清单作为提交点。崩溃后忽略未提交页，从最后已提交页恢复；任务摘要与索引可由已提交数据重建。冻结清单独立于普通任务保留策略，清理任务或缓存前验证课题档案仍可打开。

**兼容与容量。** 用一份 0.5.8 任务副本验证读取、升级写入、重启和从备份恢复。首次转换保留原件，仅补有依据的数据；旧轮次只有统计，就标明缺少逐篇清单。用默认任务上限 1,500 篇及多页样例测量保存耗时、冷启动耗时和磁盘占用。只有在分文件方案仍出现明显写入阻塞或跨课题查询瓶颈时，再据实测结果评估 SQLite。

## 四、如何判断可以发布

每阶段都通过面板和对应模型工具验证同一任务的可见状态；涉及本地文件选择和人工去重的操作从面板验收。回归样例固定上游响应，用临时数据目录模拟重启；真实来源、真实 Zotero 测试库和一次实际课题返修用于验证接口及使用结果。代码变更按影响面运行 `pnpm build`、`pnpm typecheck:client`、`pnpm build:client` 和 `pnpm test`。

首版演示只需一篇论文：精确补录，读到摘要末段，存入指定分类，关闭插件，次日关联 PDF，重新打开并核验附件。完成这条路径后，第二阶段才扩大取数；到第四阶段，再把整个课题目录移到新位置，断开原目录，逐篇核对投稿时的清单、材料及当前更新差异。
